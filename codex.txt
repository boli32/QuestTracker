QuestTracker 1.3 Codex Handoff
================================

This file is a handoff note for future Codex sessions working on this repo.
It explains the current direction of the QuestTracker v1.3 refactor and the
reason behind the recent rumour changes.

Handoff rule
------------

Every Codex session working on this repo should treat this file as shared
handoff memory.

At the start of work:

- Read codex.txt before making assumptions.
- Check git status so local uncommitted work is understood.
- Preserve any user or other-Codex changes unless the user explicitly asks for
  them to be reverted.

Before handing off, stopping, committing, pushing, or moving work between home
and work:

- Update codex.txt with the current task state.
- Note any files changed, tests/checks run, and known unfinished work.
- Keep the important design decisions current, especially decisions the user
  explicitly said not to undo.
- Do this on both sides of the workflow: the home Codex and the work Codex
  should both maintain this file whenever they touch the project.

Latest local update
-------------------

The linked quest handout command controls were changed from compact
symbol/small-button controls to full text links.

Current intended linked quest handout command style:

[ Edit | Delete | Make Priority | Use Once | Add Trigger ]

For single actions:

[ Add Rumour ]

Apply this pattern to linked quest handout commands generally, including quest
field edits, relationships, rumours, trigger summaries, trigger conditions,
trigger effects, and footer navigation.

Do not reintroduce tiny c/-/p/b/1/T rumour buttons or other compact handout
command buttons unless the user explicitly asks for that older compact layout.

Campaign flag UI/data was simplified:

- Campaign flags are status-driven in 1.3. A flag stores a name, current status,
  and its own copied status set.
- The default flag statuses are initially seeded from hard-coded values, then
  managed from Configuration/chat as the template for future flags.
- New flags ask only for the flag name, copy the current default status template
  into that flag, and start at the first copied status.
- Once a flag exists, its status set is independent. The GM can edit, add,
  delete, or copy defaults for that specific flag without changing other flags
  or the default template.
- Do not reintroduce flag true/false values, separate flag value prompts, flag
  categories, or old state/stateStatus compatibility paths.
- Campaign flags are handled entirely in chat now; there is no dedicated handout
  for them.
- The main menu Campaign Flags section renders a compact plain-text summary with
  no bullet points: colour square, quiet black flag-name link, and bracketed
  status link/dropdown coloured with that status colour. Both links use the
  scoped hover underline hook.
- Changing a flag status from the main menu passes menu=main and returns to the
  main menu after the status change.
- The only action beneath the main menu Campaign Flags summary is the standard
  black Manage Flags button.
- Flag configuration stays in chat menus:
  - !qt-menu action=flags opens the chat management menu.
  - !qt-menu action=flag|key=<flag> opens a single flag chat menu with a neat
    aligned black-button grid for Change Status, Edit Name, Statuses, and
    Delete. Status/name edits from this page pass menu=flag and return to the
    same flag page.
  - !qt-menu action=allflags is a compatibility alias to the chat flag menu.
  - !qt-menu action=flagStatuses opens the default/template status menu.
  - !qt-menu action=flagStatusSet|key=<flag> opens that specific flag's status
    set menu.
- Trigger flag effects are status-only and use the selected flag's status set.
- Quest/trigger flag requirements use a combined flag/status selector so the
  chosen status is valid for the selected flag.
- The old flags handout refresh wiring has been removed from QuestTracker.js.

Important rumour model direction
--------------------------------

The user does not want to revert the v1.3 rumour location/climate change.

Rumours no longer have their own separately managed location layer in the UI.
They are linked to a quest and status only, and the rumour location is derived
from the quest's Location field.

In practical terms:

- Quest location is the source of truth.
- That location is the climate/location key used by the calendar/weather
  location system.
- A rumour belongs to:
  - quest id
  - quest status
  - rumour id
- It should not expose separate rumour-location management to the GM.

Expected rumour shape for v1.3 is:

QUEST_TRACKER_globalRumours[questId][statusKey][rumourId] = {
  text: "...",
  type: "background" | "priority",
  once: false
}

The old nested location shape is legacy/import compatibility only and should
not be reintroduced as the active authoring model.

Do not bring back:

- All Rumours menu as a primary UI.
- Rumour details menu as a primary UI.
- Rumour locations menu.
- Chat-based Show Rumours flow.
- Manual rumour number/id entry.
- Any UI that asks the user to choose or edit a rumour location separately from
  the quest location/climate.

Current rumour UI direction
---------------------------

The GM should manage rumours from the linked quest handout.

The linked quest handout is updated under this marker:

<hr><h1>QuestTracker</h1>

Everything before that marker is preserved. Everything after that marker is
QuestTracker-generated and may be rewritten.

If the marker does not exist, QuestTracker appends the marker and generated
content to the end of the handout.

Until a quest has a linked quest handout, quest details may fall back to chat
only to tell the GM to link/create a handout. The direction is still to move
working UI into handouts where possible.

Recent rumour changes already made
----------------------------------

In 1.3/QuestTracker.js:

- Rumour add now always uses H.getNewRumourId().
- The add UI asks only for rumour text; it does not offer a rumour number.
- Rumour update preserves the existing rumour id instead of remove-and-add.
- Rumour edit/add/remove/type/once actions refresh the linked quest handout.
- The main menu no longer shows Active Rumours or Show All Rumours.
- Old rumour menu functions are compatibility redirects/stubs:
  - showAllRumours warns and opens All Quests.
  - showQuestRumourByStatus opens quest details.
  - showRumourDetails opens quest details.
  - manageRumourLocations warns that quest location is the source of truth.
- !qt-rumours action=send no longer reveals rumours to chat.
- sendRumours() now warns instead of sending /desc output.
- Trigger UI no longer offers manual rumour id entry.

Open design direction
---------------------

The user is considering default handout creation so QuestTracker can avoid chat
fallbacks for quest-specific work. Do not solve that unless asked, but keep new
UI work compatible with that direction.

When in doubt, preserve this principle:

Quest handout is the working surface. Quest location/climate is the rumour
location source of truth. Chat is for basic commands, warnings, and review
links, not for rumour management.
